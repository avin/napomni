# 13: Уточнения и восстановление LLM

У каждой отправленной команды есть независимый UUID приложения. Он сохраняется в `CommandContext` вместе с исходным UTC, местным временем и выбранным ID записи; повтор получения ответа использует тот же контекст. Новая команда получает новый UUID, даже при том же тексте и повторно использованном провайдером call ID.

`execute_tool_once` проверяет сохранённый результат по паре `(UUID команды, ID вызова)`. Имя инструмента и разобранные аргументы привязаны к этой паре: другое содержимое с тем же ID отклоняется. Изменение данных сначала выполняется на подготовленном состоянии с хранилищем в памяти, затем реальные данные и результат инструмента записываются одним атомарным сохранением. При отказе записи ничего не публикуется; повтор можно выполнить после восстановления диска. Повтор успешного вызова возвращает прежний результат без повторного создания, изменения, удаления, паузы или отмены.

До сетевого запроса `ChatSession` сохраняет незавершённую команду с типизированными сообщениями Chat Completions. Ошибка ответа оставляет её для действия «Продолжить ответ», включая новый запуск приложения. Продолжение отправляет сохранённые assistant/tool сообщения, не создавая новую пользовательскую команду. Если приложение завершилось после сохранения данных и результата инструмента, но до сохранения переписки, продолжение восстанавливает недостающие пары assistant/tool из результатов в порядке выполнения.

Успешный результат инструмента сразу передаётся в интерфейс и сохраняется в чат; итоговый текст модели для применения операции не требуется. Повтор результата не добавляет один и тот же факт снова в ходе обработки. Обычный ответ/уточнение сам по себе не меняет напоминания. Выбранный ID остаётся до фактической операции или явного снятия выбора, поэтому ответ на уточнение относится к нужной записи, даже если тексты совпадают.

Ключи подключения скрываются в истории и файле продолжения, включая отражённые провайдером assistant/tool данные и вложенный JSON. Привязки вызовов, UUID и временной контекст сохраняются. При смене ключа во время запроса старый и новый ключи остаются известны текущему сеансу для скрытия позднего ответа. Сами напоминания и атомарные результаты инструментов содержат фактические пользовательские данные; ключ конфигурации не добавляется в них автоматически.

Все блокировки ядра ограничены локальными операциями; сетевые await выполняются без них. Локальный планировщик работает во время ожидания и ошибки API.

Проверки (согласованные границы ядра/хранилища и локального HTTP):

- Четыре HTTP-сценария: сбой итогового ответа и продолжение с результатом инструмента; восстановление после сбоя до сохранения переписки; уточнение с выбранным ID и точечное изменение; задержанный ошибочный ответ API одновременно с офлайн-срабатыванием.
- Пять прикладных сценариев: результат сохраняется после перезапуска и не смешивается с другой идентичной командой; данные и результат сохраняются атомарно; повтор не применяет паузу/удаление/отмену заново после последующих действий; неверные аргументы, ID и неподдерживаемое правило не меняют данные/отмену; история и продолжение не содержат текущий/старый ключ даже при вложенном JSON.
- Ранее созданные проверки04/05 покрывают задержанные относительные команды, «завтра» через полночь, устаревшее время, одинаковый текст разных ID, сохранность остальных свойств. Проверки02 покрывают несовместимую модель и сетевые ошибки.
