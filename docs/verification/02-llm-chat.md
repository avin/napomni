# Готовый клиент Chat Completions

Для соединения используем async-openai 0.28.3 с явно заданными URL, ключом и моделью. Протокол, сериализацию сообщений и tool calls реализует библиотека; прикладное ядро остаётся владельцем проверки аргументов и фактических результатов инструментов.

Проверена документация Rig: библиотека поддерживает инструменты и их цикл, а OpenAI-провайдер по умолчанию использует Responses API. Произвольный base URL сам по себе не препятствует использованию Rig. Однако автоматическое исполнение инструментов внутри агента не соответствует выбранному разделению ответственности: приложению нужно сохранять фактический результат до запроса финального текста, переживать ошибку этого запроса без повторной мутации и проверять именно Chat Completions у произвольного провайдера. Вместо второго владельца цикла используем готовый async-openai с типизированными сообщениями и tool calls. Это архитектурный выбор, а не утверждение об отсутствии поддержки Chat Completions у Rig.

Обычный чат использует tool_choice=auto. Отдельная проверка требует connection_probe(ok=true) и проверяет фактическое имя и аргументы. Этот инструмент не имеет доступа к напоминаниям. Ключ лежит в connection.json открытым текстом; ошибки провайдера представлены локальными русскими сообщениями без пересылки сырого ответа. История хранится отдельно в chat.json; входящий и исходящий текст с текущим ключом редактируется перед сохранением.

Источники: [Rig tools](https://docs.rig.rs/docs/concepts/tools), [async-openai config](https://docs.rs/async-openai/0.28.3/async_openai/config/struct.OpenAIConfig.html).

Автоматические проверки: cargo fmt --check, cargo clippy --locked --all-targets -- -D warnings, cargo test --locked. HTTP-стенд работает только на 127.0.0.1 и не вызывает платного провайдера. Проверены обычный ответ, обязательный фактический безопасный tool call, отказ модели вызывать инструмент, ошибки ключа/модели/URL/сети, повторное открытие хранилища и очистка истории.

Настоящий ввод, IME, масштаб Windows и отзывчивость окна при ожидании провайдера требуют визуального прогона на Windows. В этой задаче они ещё не подтверждены. Поля реализованы через GPUI EntityInputHandler с UTF-16/UTF-8, выделением, буфером обмена и клавиатурной навигацией; исходник адаптирован из GPUI examples/input.rs.
